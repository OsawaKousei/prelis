# 開発規則

人間と AI エージェントに共通する開発上の規則です。
現在の構成は[アーキテクチャ](../architecture.md)、実行手順は[作業・検証手順](workflow.md)に記載しています。

## 機能開発の方針

[トップレベルの基本原則](../../AGENTS.md)を、仕様・実装・検証に適用します。

- 機能仕様と機能としての受け入れ条件は両アプリで共通にします。UI の差分は機能の差分と分けて記述します。
- 新しい機能はデスクトップで実装・確認してからモバイルへ反映します。デスクトップ確認済みとモバイル反映済みを区別し、反映待ちの内容を記録します。
- UI は各アプリで個別に実装します。モバイルの画面構成・操作方法は端末の特徴に合わせて変更できますが、共通の提供機能と受け入れ条件を維持します。視覚・操作デザインは[デザインガイドライン](../design/guidelines.md)を参照します。
- デスクトップで先行開発する場合も、core の変更が既存のモバイル機能を壊さないことを確認します。

## 作業範囲

- 作業依頼と関連する仕様を確認し、依頼に必要な変更を行います。未確定の製品仕様を既存仕様として扱いません。
- 既存の未コミット変更を確認し、作業対象外の変更を上書き・巻き戻ししません。
- 現在の開発対象はデスクトップと Android です。iOS 固有の整備は対応を再開するタスクで扱います。
- `ref/` は通常の変更対象に含めません。タスクで指定された参考資料を扱う場合は、その指定範囲を参照します。

## コードの境界

- `packages/core` に UI・OS に依存しないロジックを置き、DOM・React Native・Tauri の API を直接持ち込みません。
- OS 固有処理は各アプリに置き、共有ロジックから必要な処理は関数・インターフェースとして注入します。
- アプリから core を使う場合は公開エントリ `@prelis/core` を使用し、別 workspace の内部ファイルを相対パスで import しません。
- デスクトップ固有の UI は React、ネイティブ処理は `src-tauri/` に配置します。
- モバイル固有の UI は React Native、Android 固有の設定・ネイティブ処理は `android/` に配置します。
- 既存ファイルの書式と各アプリの設定に合わせ、機能変更と無関係な一括整形を避けます。

## 依存・ビルド設定

- npm を使用し、ルートの lockfile で全 workspace の依存を管理します。アプリ別の lockfile を作りません。
- 依存追加・更新はルートから対象 workspace を指定して行い、package.json と lockfile を一緒に更新します。
- React・React DOM・React Test Renderer と React Native の renderer の整合を維持します。
  バージョンを変更するときはルートの `overrides`、両アプリの宣言、依存ツリーをまとめて確認します。
- Vite・Metro が core のソースを読む構成を維持します。公開エントリやバンドラーの変更は両アプリへの影響を検証します。
- Metro の階層探索を無効化する場合は、ネストされた依存も含めて解決できる構成と検証が必要です。
- Android のネイティブ依存はルートへ配置される前提です。Gradle のパスをアプリ内の `node_modules/` に戻さないでください。
- SDK・JDK・ポートなどを変更するときは、関連する開発手順と設定ファイルの整合を確認します。

## 生成物・ローカル設定

- `node_modules/`、`dist/`、Rust の `target/`、Android の `build/` などの生成物を Git に追加しません。
- `local.properties`、署名鍵、認証情報、マシン専用の秘密情報は Git に追加しません。
- 一般的な必要条件は開発手順へ、共有できるマシン固有の導入先・確認履歴は環境メモへ記録します。
- 一時的な検証で変更したサンプル文言などは元に戻し、自分が起動した検証用プロセスは終了させます。

## 検証と完了報告

- [変更別の検証表](workflow.md)に沿って、変更の影響を確認できる検証を選びます。
- 振る舞いを変更した場合は、その振る舞いを確認するテストを追加・更新します。実装の写しだけになるテストは増やしません。
- JavaScript バンドル成功とネイティブビルド成功、ビルド成功と画面上の動作確認を区別します。
- 実行できなかった検証は理由と未確認範囲を明記し、過去の確認結果を今回の結果として報告しません。
- 基本原則はトップの AGENTS.md に、詳細な規則・手順・仕様は docs に記載します。変更時は関連文書の整合を保ち、README や AGENTS.md に詳細を重複記載しません。
